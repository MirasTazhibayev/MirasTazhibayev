## 11.
Для всех запросов нужен вход. Пользователь работает только со своими задачами.

| Операция | Запрос | Ответ |
|---|---|---|
| Создание | POST /api/tasks | 201 |
| Список | GET /api/tasks?limit=20 | 200 |
| Просмотр | GET /api/tasks/42 | 200 |
| Изменение статуса | PATCH /api/tasks/42 | 200 |
| Удаление | DELETE /api/tasks/42 | 204 без тела |

Создание:
```http
POST /api/tasks
Content-Type: application/json

{"title":"Сделать отчет"}
```
Ответ:
```http
HTTP/1.1 201 Created
Location: /api/tasks/42

{"id":42,"title":"Сделать отчет","status":"todo","version":1}
```
Просмотр GET /api/tasks/42 возвращает этот объект с кодом 200.

Изменение:
```http
PATCH /api/tasks/42
Content-Type: application/json

{"status":"done","version":1}
```
Ответ 200:
```json
{"id":42,"title":"Сделать отчет","status":"done","version":2}
```
Разрешенные статусы: todo, in_progress, done.

Для страниц можно использовать cursor:
```json
{
  "items":[{"id":42,"title":"Сделать отчет","status":"done","version":2}],
  "next_cursor":"cursor-value"
}
```
Следующий запрос: GET /api/tasks?limit=20&cursor=cursor-value. В конце next_cursor равен null. Нужна стабильная сортировка, например по created_at и id.

Ошибки: 400 — неправильный JSON или cursor; 401 — нет входа; 403 — нет прав; 404 — задача не найдена; 409 — конфликт версии; 422 — неверные поля; 429 — слишком много запросов; 500 — ошибка сервера.

Пример ошибки:
```json
{"error":{"code":"validation_error","fields":{"title":"Введите название задачи"}}}
```

|---|---|---|

## 24.
Если операции отдельные, остаток может уменьшиться без заказа или заказ появится без изменения остатка. Два покупателя также могут купить последний товар одновременно.

В одной БД использовать транзакцию:
```sql
BEGIN;

UPDATE products
SET stock = stock - :qty
WHERE id = :product_id AND stock >= :qty;

-- Если обновлено 0 строк: отменить транзакцию и вернуть ошибку.
-- Если обновлена 1 строка: создать заказ и его позиции.

COMMIT;
```
Количество должно быть положительным целым. При нехватке товара вернуть 409. При ошибке создания заказа сделать ROLLBACK, чтобы остаток восстановился. В БД дополнительно запретить отрицательный stock.

Для нескольких товаров блокировки брать в одинаковом порядке. Если БД и оплата находятся в разных сервисах, нужны резервирование и компенсация при сбое, потому что одна транзакция БД не охватывает внешний платеж.

При уходе со страницы отменить запрос, например через CancelToken в Dio, и закрыть подписки. Перед изменением состояния проверить mounted и актуальность запроса:
```dart
final requestId = ++_requestId;
final items = await repository.load(cancelToken: _cancelToken);

if (!mounted || requestId != _requestId) return;
setState(() => _items = items);
```
Ошибки обрабатывать через try/catch. В dispose отменить запрос, увеличить _requestId и освободить ресурсы. Для нового запроса использовать новый токен отмены.

## 26.
| Уровень | Что проверить |
|---|---|
| Unit | Пустое обязательное поле и только пробелы дают ошибку |
| Unit | Неверный email отклоняется, корректный принимается |
| Unit | Ограничения длины работают на границах |
| Интеграция | Валидный запрос создает пользователя, пароль хранится как хеш |
| Интеграция | Занятый email не создает второго пользователя |
| Интеграция | Два одновременных запроса с одним email создают только одного пользователя |
| Интеграция | Прямой запрос без обязательного поля отклоняется |
| UI | Ошибки показаны рядом с полями |
| UI | Сообщение о занятом email видно пользователю |
| UI | После исправления формы регистрация проходит |
| UI | При сетевой ошибке данные сохраняются и доступен повтор |

Уникальность email нужно проверять не только в приложении, но и ограничением БД.

## 27.
Пусть скидка 10% применяется от 10 000 KZT включительно.

| Сумма | Скидка | Итог |
|---|---:|---:|
| 9 999,99 | 0 | 9 999,99 |
| 10 000,00 | 1 000,00 | 9 000,00 |
| 10 000,01 | 1 000,00 | 9 000,01 |

Здесь скидка округляется до двух знаков. Если расчет только в целых тенге, проверить 9 999, 10 000 и 10 001.

Еще нужны проверки нулевой суммы, отрицательной суммы, обычной суммы выше порога, максимальной суммы и некорректного процента скидки.

Для этой логики подходят unit-тесты и проверка граничных значений. Деньги считать через Decimal или целые минимальные единицы, чтобы избежать ошибок float.

## 28.
| Сценарий | Ожидаемый результат |
|---|---|
| Товар есть, данные правильные | 201, номер заказа, остаток уменьшен |
| Количество равно остатку | Успех, остаток стал 0 |
| Товара недостаточно | 409, заказ не создан, остаток прежний |
| Товар не найден | 404 |
| Количество 0, отрицательное или дробное | 422 |
| Пользователь не вошел | 401 |
| Запрос от имени другого пользователя | Отказ; владельца определяет сервер |
| Ошибка записи заказа | Откат, остаток не потерян |
| Два запроса на последний товар | Только один успешный заказ |
| Повтор с тем же ключом идемпотентности | Тот же заказ без повторного списания остатка |
| Тот же ключ с другими данными | 409 |

Интеграционный тест должен проверить ответ API и реальные записи в тестовой БД: заказ, позиции и остаток. Отдельно проверить откат при сбое и одновременные запросы через разные соединения.

## 29.
Сначала проверить саму библиотеку: правильные и неправильные токены, подпись, срок действия, issuer, audience и роли.

Потом проверить веб- и мобильный клиент: вход, выход, обновление токена, отзыв сессии, MFA и восстановление доступа. Важно проверить совместимость со старой поддерживаемой версией приложения.

В регрессию включить доступ к чужим данным, запрещенные роли, другую организацию, истекшие и поврежденные токены. Для веба проверить cookie, CSRF и CORS, для телефона — хранение токена, перезапуск и сетевые ошибки.

Интеграционные и E2E-тесты помогут увидеть побочные эффекты в обоих клиентах. В логах не должны появляться пароли и токены.

## 30.
| Случай | Действие | Ожидаемый результат |
|---|---|---|
| Загрузка | Открыть экран с задержанным ответом | Видно загрузку, а не пустой список |
| Список | Вернуть несколько элементов | Данные показаны, открывается нужный элемент |
| Пустое состояние | Вернуть пустой список | Сообщение об отсутствии данных |
| Ошибка | Вернуть 500 или сетевой сбой | Ошибка и кнопка повтора |
| Повтор | После ошибки вернуть данные | Появляется список, ошибка исчезает |
| Обновление | Свайпнуть список | Данные обновляются без дублей |
| Ошибка обновления | Сбой после успешной загрузки | Старые данные остаются, ошибка видна |
| Поворот | Повернуть экран при загрузке и со списком | Нет переполнения и лишних запросов |
| Возврат | Открыть подробности и вернуться | Фильтр и позиция сохранены, изменения видны |
| Уход со страницы | Закрыть экран до ответа | Запрос отменен, нет обновления уничтоженного экрана |
| Смена фильтра | Быстро выбрать два фильтра | Показан ответ последнего фильтра |

Автоматически проверять логику состояния, загрузку, ошибки, повтор, навигацию и отмену запросов. Для UI подойдут widget-тесты с тестовым API.

Вручную проверить удобство свайпа, читаемость, поворот на разных устройствах, крупный шрифт и экранный диктор.
