## 2. Доступ к чужому заказу
Это IDOR, а для API — BOLA: нарушение авторизации на уровне объекта. Сервер ищет заказ по номеру, но не проверяет владельца.

## 4. Безопасная загрузка аватарок
При загрузке проверить авторизацию, CSRF при cookie-сессиях, лимит частоты, размер файла, число пикселей и разрешенные форматы, например JPEG и PNG. Проверить сигнатуру и успешно декодировать изображение: MIME клиента недостоверен. Использовать обновленный декодер с ограничением ресурсов.

При хранении создать случайное имя, не использовать путь клиента, хранить вне исполняемого каталога с запретом запуска и минимальными правами.

## 5. SQL-инъекция
Конкатенация email позволяет изменить структуру SQL-запроса. Безопасный вариант — параметризованный запрос. Пример для Python sqlite3:
```python
cursor.execute("SELECT id, email FROM users WHERE email = ?", (email,))
```
В другом драйвере синтаксис параметров может отличаться. Значение передается отдельно от SQL; ручное экранирование не является основным решением.
Еще две меры ограничения ущерба:
- выделенная учетная запись БД с минимальными правами, без администрирования и ненужной записи;
- раздельный доступ к чувствительным данным: учетная запись этого компонента не может читать платежные данные или секреты, которые ему не нужны.

## 6. SSRF при загрузке изображения по URL
Опасны localhost, loopback, приватные сети, link-local и облачные metadata-адреса, служебные внутренние домены, IPv6-эквиваленты и IPv4-mapped IPv6. DNS может вернуть внутренний адрес, несколько адресов или изменить ответ между проверкой и подключением. Перенаправление может вести с разрешенного адреса на внутренний.
Лучше разрешить только заранее определенные HTTPS-домены и порты. Разбирать URL стандартным парсером, запрещать credentials в URL и схемы file, ftp и другие ненужные схемы.
Проверять все A/AAAA-адреса и адрес фактического подключения, учитывать смену DNS. Соединение должно использовать проверенный адрес с корректной проверкой TLS и hostname. Редиректы отключить либо проверять каждый переход теми же правилами.
Дополнительно ограничить исходящий трафик через proxy/firewall, закрыть metadata и внутренние сети, задать тайм-ауты, максимальный размер ответа, число редиректов и проверку формата изображения.

## 10. Модель угроз сервиса записи к врачу
Защищаемые данные: имя, контакты, идентификаторы пациента, учетные данные, врач, дата приема и медицинские сведения, если они собираются. Даже факт записи к определенному специалисту может быть чувствительным.
| Угроза | Точки входа | Меры |
|---|---|---|
| Чтение чужих записей | API записи и личный кабинет | Проверка владельца и организации на каждом запросе |
| Захват аккаунта | Вход, восстановление пароля | MFA сотрудников, лимиты попыток, безопасное восстановление |
| Инъекция или вредоносный ввод | Формы, поиск, API | Параметризация SQL, серверная валидация, безопасный вывод |
| Утечка через сотрудника | Панель врача/регистратуры, экспорт | Роли, доступ по необходимости, аудит и ограничения выгрузок |
| Недоступность сервиса | Публичный API | Rate limit, резервирование и проверяемые резервные копии |
Использовать TLS, шифрование хранения, ограниченные сроки хранения и исключать медицинские данные из технических логов. Увольнение или смена роли должны немедленно менять права; экстренный расширенный доступ отдельно обосновывается и журналируется.
После утечки ограничить доступ, сохранить свидетельства, определить затронутые данные и людей, восстановить сервис и исправить причину. Уведомления согласовать с ответственными и применимыми требованиями.

## 11. API списка задач
Все операции требуют аутентификации и проверки владельца. Поля задачи: id, title, status, version, created_at. Допустимые статусы: todo, in_progress, done.
| Действие | Запрос | Успешный ответ |
|---|---|---|
| Создать | POST /api/tasks | 201 Created и Location |
| Список | GET /api/tasks?limit=20&cursor=... | 200 OK |
| Одна задача | GET /api/tasks/42 | 200 OK |
| Изменить статус | PATCH /api/tasks/42 | 200 OK |
| Удалить | DELETE /api/tasks/42 | 204 No Content |

Создание:
```http
POST /api/tasks
Content-Type: application/json

{"title":"Подготовить отчет"}
```
```http
HTTP/1.1 201 Created
Location: /api/tasks/42

{"id":42,"title":"Подготовить отчет","status":"todo","version":1}
```
Просмотр `GET /api/tasks/42` возвращает тот же объект с кодом 200.
Изменение:
```http
PATCH /api/tasks/42
Content-Type: application/json

{"status":"done","version":1}
```
Ответ 200: `{"id":42,"title":"Подготовить отчет","status":"done","version":2}`.
Удаление `DELETE /api/tasks/42` возвращает 204 без тела.

Список:
```json
{
  "items":[{"id":42,"title":"Подготовить отчет","status":"done","version":2}],
  "next_cursor":"opaque-server-generated-cursor"
}
```
В конце списка next_cursor равен null. Сортировка стабильная, например created_at и id; курсор привязан к фильтрам. Сервер ограничивает limit диапазоном 1–100.
Ошибки: 400 — поврежденный JSON или курсор; 401 — нет действительного входа; 403 — запрещенное действие; 404 — доступная задача не найдена; 409 — конфликт version; 422 — некорректные поля; 429 — превышен лимит; 500 — внутренняя ошибка.
Пример: `{"error":{"code":"validation_error","fields":{"title":"Введите название от 1 до 200 символов"}}}`.

## 12. Повтор создания заказа после тайм-аута
Клиент один раз создает случайный Idempotency-Key для конкретного оформления и сохраняет его до получения окончательного результата. После тайм-аута повторяет тот же запрос с тем же ключом. Новый заказ получает новый ключ; блокировка кнопки дополнительно предотвращает случайные нажатия.
Сервер хранит ключ в области пользователя и операции, хеш тела, состояние и результат. Уникальный индекс не дает двум одновременным запросам занять один ключ. Создание заказа и фиксация результата ключа выполняются атомарно.
Завершенный повтор возвращает прежний order_id и согласованный ответ; тот же ключ с другим телом — 409. Если первый запрос еще выполняется, повтор ждет ограниченное время либо получает статус обработки и способ проверки.
Срок хранения ключа должен покрывать окно повторов. Для платежа использовать собственную идемпотентность провайдера: транзакция локальной БД не делает внешний вызов атомарным.

## 13. Одновременное изменение записи
Использовать оптимистическую блокировку. При чтении вернуть version = 7; клиент отправляет новую запись и ожидаемую версию.
```sql
UPDATE tasks
SET title = :title, version = version + 1
WHERE id = :id AND owner_id = :user_id AND version = :expected_version;
```
Если изменена одна строка — вернуть новую версию. Если ни одной — отдельно проверить наличие доступной записи: 404 при отсутствии, 409 при конфликте. Клиент загружает свежую запись и предлагает объединить изменения; автоматически перезаписывать ее нельзя.
Альтернатива — ETag и If-Match с 412 Precondition Failed. Сравнение версии и запись должны быть одной атомарной операцией.

## 14. Endpoint стал медленнее
Сравнить период до и после изменения: p50/p95/p99 задержки, RPS, ошибки, CPU, память, GC, дисковый ввод-вывод и очередь запросов. Проверить недавние релизы и изменение нагрузки.
Использовать request_id и распределенные трассировки, разделяющие время БД, внешнего API, сети и кода.
- БД: медленные запросы, план EXPLAIN в безопасной среде, индексы, блокировки, ожидание пула соединений, количество запросов и N+1.
- Сеть: DNS, TCP/TLS, потеря пакетов, повторные соединения и объем передаваемых данных.
- Внешний сервис: длительность вызова, тайм-ауты, ответы 429/5xx и его состояние.

Если SQL выполняется быстро, но запрос долго ждет соединения, причина может быть в пуле, а не самом SQL. Сначала воспроизвести проблему и измерить, затем менять конкретный узкий участок.

## 15. Валидация даты рождения и email
Frontend: обязательность, понятный формат даты, существующая дата, запрет будущей даты, базовый формат email. Возрастные ограничения применять только если они заданы бизнес-правилами.
Backend повторяет проверки независимо от клиента, ограничивает длину, проверяет типы и допустимые значения. Дату рождения хранить как календарную DATE без сдвигов часового пояса. Email обрабатывать по определенной политике нормализации, не менять бездумно локальную часть.
Если email уникален, установить уникальное ограничение БД: предварительной проверки недостаточно при одновременных запросах. Подтверждение письмом проверяет владение адресом, чего не делает regex.
Ошибки вернуть по полям с 422, показать возле соответствующего поля, сохранить остальные значения и перевести фокус на первую ошибку. Примеры: «Дата не может быть в будущем», «Проверьте формат email». SQL и stack trace пользователю не показывать.

## 16. Offset- и cursor-пагинация
| Критерий | Offset | Cursor |
|---|---|---|
| Пример | LIMIT 20 OFFSET 1000000 | WHERE (created_at,id) > (:date,:id) LIMIT 20 |
| Большая глубина | Обычно нужно обработать пропущенные строки | Эффективный переход при подходящем индексе |
| Переход к странице 50 | Простой | Обычно нужен известный курсор |
| Изменения данных | Вставки/удаления сдвигают страницы | Меньше сдвигов при стабильном ключе |
| Типичное применение | Небольшая таблица, нумерованные страницы | Миллионы строк, бесконечная прокрутка |

Для миллионов записей выбрать cursor с индексом под фильтр и сортировку. Ключ сортировки должен иметь уникальный дополнительный id. Курсор кодирует последнюю позицию и соответствует текущим фильтрам; кодирование не дает права доступа.
Для маленького справочника и переходов по номерам страниц подойдет offset. Cursor не создает снимок данных автоматически: при изменении поля сортировки тоже возможны пропуски. Если нужен неизменный экспорт, использовать согласованный снимок или фиксированную границу выборки.

## 17. Работа с платежным API
Установить тайм-ауты подключения и ответа, учитывать общее время операции. При тайм-ауте платежа результат неизвестен: провайдер мог списать деньги, но ответ потерялся.
Для создания платежа использовать постоянный ключ идемпотентности. Проверить статус по идентификатору операции или ключу; обработать подписанный webhook с дедупликацией и защитой от повторного применения.
Повторять временные ошибки ограниченно, с exponential backoff и jitter. При 429 учитывать Retry-After и лимиты провайдера; ошибки валидации и отказ оплаты автоматически не повторять.
При длительной недоступности применить circuit breaker, очередь и состояние pending; пользователь видит «Платеж проверяется», а не ложное подтверждение.
Нельзя слепо повторять списание, перевод, возврат и другие денежные операции. Проверка статуса, идемпотентность и сверка предотвращают двойную обработку.

## 18. Аутентификация и авторизация
Аутентификация отвечает «Кто пользователь?» — например, проверяет пароль и MFA.
Авторизация отвечает «Что ему разрешено?» — например, разрешает читать только собственные заказы.
Ошибка: пользователь вошел и меняет /orders/1842 на /orders/1843, после чего видит чужой заказ. Вход проверен, но проверка владельца отсутствует. Авторизацию выполнять на сервере для каждого объекта и действия.

## 19. Модель, инструменты и приложение ИИ-агента
Модель понимает задачу, предлагает план, анализирует найденные данные и составляет черновик письма. Инструменты выполняют конкретные операции поиска и отправки. Приложение управляет учетной записью, правами, подтверждениями, лимитами и журналом.
Самостоятельно агент может искать сведения в разрешенных источниках, проверять неоднозначность клиента и готовить черновик в пределах задания.
Перед отправкой приложение показывает человеку точного получателя, тему, текст и вложения. В этой схеме внешняя отправка, изменение клиентских данных и массовые действия требуют подтверждения. Можно предусмотреть заранее согласованную узкую автоматизацию, но ее границы задает приложение.
Поиск не дает право отправлять письмо любому найденному адресу. Разрешение связывается с конкретным действием и содержимым, а не с произвольным следующим вызовом модели.

## 20. Инструкция внутри документа
Это prompt injection: недоверенное содержимое пытается управлять агентом.
Документы и веб-страницы передавать как данные с обозначенным источником и границами, а не вставлять как системную инструкцию. Фраза из документа не может изменять правила приложения или разрешать передачу информации.
Ограничить доступные инструменты, адреса назначения и данные; проверять аргументы и права вне модели. Для передачи чувствительных данных требовать разрешенное назначение и подтверждение.
Не помещать секреты в контекст без необходимости. Проверять систему на документы со скрытыми инструкциями и попытками обхода. Одного предупреждения в prompt недостаточно: надежные ограничения выполняет приложение.

## 21. Ограничение инструментов агента
- search_customer: область текущей организации и разрешенные поля, ограничение результатов и частоты. Результат не включает ненужные секреты.
- update_customer: разрешенный customer_id, список изменяемых полей, версия записи и проверка роли. Изменение прав, организации и платежных реквизитов через общий инструмент запрещено.
- send_email: проверенные получатели, лимит адресатов, проверка вложений и подтверждение точного черновика.
Проверять JSON-схемы, типы, длины и бизнес-правила на сервере. Tenant и права брать из доверенной сессии, а не из произвольных аргументов модели.
Журналировать пользователя, действие, время, request_id, факт подтверждения, безопасные параметры и результат; секреты и лишние персональные данные маскировать.
После обновления проверить сохраненную версию и разрешенные изменения; после отправки сохранить message_id и статус, не считать прием письма сервисом доказательством доставки.
Против массовых изменений: лимиты количества и частоты, запрет wildcard, предварительный просмотр, отдельное подтверждение пакетной операции и возможность остановки.

## 22. Сравнение версий инструкции агента
Создать набор обычных, сложных, неоднозначных и атакующих запросов, ошибок инструментов и разных языков. Для каждого определить ожидаемое действие и запрещенные действия. Разделить примеры разработки и независимую проверочную выборку.
Сравнивать старую и новую версии на одинаковых данных, модели, настройках и имитированных инструментах. Выполнить несколько запусков, поскольку ответы могут отличаться.
Метрики: доля успешно выполненных задач, правильность аргументов инструментов, число неподтвержденных действий, утечки, устойчивость к injection, обоснованность ответа, задержка, число вызовов и стоимость.
Результаты анализировать по категориям, а не только по среднему значению. Пять улучшенных примеров не доказывают общий прогресс. Опасные действия считаются блокирующим ухудшением; новую версию выпускать после регрессии и ограниченного пилота.

## 23. Состояния frontend-списка
При первой загрузке показать индикатор или skeleton. Успешный пустой ответ — отдельное сообщение «Ничего не найдено» и возможность сбросить фильтр.
При ошибке первой загрузки показать понятное сообщение и «Повторить». При обновлении уже загруженного списка сохранить его и показать, что обновление не удалось.
При частичном результате оставить загруженные элементы и показать ошибку догрузки; повторять только неудавшуюся страницу, исключая дубли по id.
При смене фильтра отменить прежний запрос через AbortController и увеличивать request generation. Ответ применять только если его generation и фильтр совпадают с текущими. Одной отмены недостаточно: ответ мог уже прийти. Debounce уменьшает число запросов, но сам не предотвращает устаревший ответ.

## 24. Остаток товара и создание заказа
Если операции независимы, остаток может уменьшиться без заказа либо заказ появится без уменьшения остатка. Два покупателя могут одновременно прочитать остаток 1 и оба оформить покупку.
Для одной БД использовать транзакцию и атомарное условное обновление:
```sql
BEGIN;
UPDATE products
SET stock = stock - :qty
WHERE id = :product_id AND stock >= :qty;
-- Если изменено 0 строк: ROLLBACK, вернуть нехватку товара.
-- Если изменена 1 строка: INSERT INTO orders ...; INSERT INTO order_items ...;
COMMIT;
```
Количество заранее проверить как положительное целое; отличать отсутствующий товар от нехватки остатка. При ошибке записи заказа откатить транзакцию. Дополнительно CHECK stock >= 0 и идемпотентность создания.
Для нескольких товаров блокировки брать в одинаковом порядке, обрабатывать deadlock ограниченным повтором. Для разных сервисов использовать резервирование, outbox и saga с компенсацией; обычная локальная транзакция не охватывает внешнюю оплату.

## 25. Flutter-экран списка
UI содержит состояния loading, data, empty и error, RefreshIndicator и ListView. Для короткого или пустого списка использовать AlwaysScrollableScrollPhysics, чтобы свайп обновления работал.
Repository выполняет API-запросы и преобразует JSON. Controller/ViewModel или BLoC хранит состояние, фильтры и бизнес-логику; виджет отображает состояние и передает события.
Обновление свайпом возвращает Future, завершающийся после загрузки. При ошибке обновления старый список остается видимым. При нажатии передать id в экран подробностей; после изменения задачи обновить список или соответствующий элемент.
При уходе со страницы отменить запрос, например CancelToken в Dio, закрыть подписки и контроллеры. Отброшенные и устаревшие ответы не должны менять состояние.
```dart
// Схема для локального State; repository поддерживает cancelToken.
final requestId = ++_requestId;
try {
  final items = await repository.load(cancelToken: _cancelToken);
  if (!mounted || requestId != _requestId) return;
  setState(() => _items = items);
} catch (error) {
  if (!mounted || requestId != _requestId) return;
  // Отмену отличаем от ошибки; реальную ошибку отображаем в UI.
}
```
В dispose увеличить _requestId, отменить токен, освободить ресурсы и вызвать super.dispose(). Для каждого нового запроса создать новый токен; отмененный токен повторно не использовать. Код — иллюстрация защиты жизненного цикла, а не полный Flutter-проект.

## 26. Проверки регистрации
| Уровень | Случаи и ожидаемый результат |
|---|---|
| Unit | Пустое обязательное поле и только пробелы → ошибка |
| Unit | Email без @ или домена → ошибка; корректный адрес → принят |
| Unit | Длины на минимуме, максимуме и за пределами → результат по правилам |
| Интеграция | Валидный запрос → пользователь создан, пароль хранится как стойкий хеш |
| Интеграция | Занятый email → согласованный код ошибки, новая запись не создается |
| Интеграция | Два одновременных запроса с одним email → только один пользователь |
| Интеграция | Прямой запрос без обязательных полей → отказ независимо от frontend |
| UI | Ошибка привязана к полю, значения сохраняются, после исправления отправка успешна |
| UI | Занятый email отображает предусмотренное сообщение |
| UI | Во время отправки нет повторного нажатия; сеть недоступна → доступен повтор |

Использовать тестовые данные; фактическую уникальность гарантирует БД. Проверка UI не заменяет интеграционный тест ограничения.

## 27. Границы скидки
Пусть порог 10 000 KZT, скидка 10%, правило — сумма не меньше порога. При расчетах с тиынами:
| Сумма | Скидка | Итог |
|---|---:|---:|
| 9 999,99 | 0 | 9 999,99 |
| 10 000,00 | 1 000,00 | 9 000,00 |
| 10 000,01 | 1 000,00 после округления | 9 000,01 |

Также проверить 0, обычную сумму ниже и выше порога, отрицательную сумму, максимально допустимую сумму, скидку 0% и 100%, некорректные проценты. Если система принимает только целые тенге, ближайшие границы — 9 999, 10 000 и 10 001.
Подходит unit-тестирование с анализом граничных значений и классами эквивалентности. Использовать Decimal или целые минимальные денежные единицы, зафиксировать правило округления. Пример выше округляет скидку до двух знаков; иное правило должно быть явно задано.

## 28. Мини-набор проверок создания заказа
| Сценарий | Ожидаемое поведение |
|---|---|
| Достаточный остаток, валидный запрос | 201, order_id, заказ и позиции записаны, остаток уменьшен |
| Количество равно остатку | Успех, новый остаток 0 |
| Остаток меньше количества | 409 stock_insufficient, без заказа и изменения остатка |
| Товар не существует | 404, без записей |
| Количество 0, отрицательное или дробное | 422, без изменений |
| Нет аутентификации | 401 |
| Попытка создать заказ от другого пользователя | Отказ; владелец определяется сервером |
| Ошибка INSERT после уменьшения остатка | Откат всей транзакции, без частичного результата |
| Два покупателя и последний товар | Один успех, второй отказ, stock неотрицательный |
| Повтор с тем же Idempotency-Key | Тот же заказ, остаток повторно не уменьшается |
| Тот же ключ с другим телом | 409 |

Интеграционный тест использует тестовую БД реального типа и проверяет HTTP-ответ, записи заказа/позиций, остаток, ограничения и откат. Конкурентность проверять двумя независимыми соединениями. Сбой вставки воспроизвести контролируемо; платежный сервис заменить тестовым адаптером.

## 29. Регрессия общей авторизации
Unit-тесты библиотеки: проверка подписи, срока действия, issuer/audience, ролей, пустого и поврежденного токена; неверный алгоритм и ключ должны отклоняться.
Контрактные и интеграционные тесты: веб- и мобильный клиент используют совместимые форматы, правильно получают 401/403, обновляют токен и обрабатывают отзыв сессии. Проверить ротацию ключей и параллельный refresh согласно принятому протоколу.
Регрессия: вход, выход, MFA, восстановление доступа, истечение сессии, запрещенные роли, чужие объекты и другая организация.
Для веба проверить cookie-флаги, CSRF и CORS; для мобильного приложения — безопасное хранение, восстановление после перезапуска и сетевой сбой.
E2E выполнить для обоих клиентов, включая поддерживаемую старую версию мобильного приложения. Проверить, что отказ в доступе не превращается в разрешение и что логи не содержат токены.

## 30. Flutter: мини тест-кейсы
| Случай | Шаги | Ожидаемый результат |
|---|---|---|
| Загрузка | Открыть экран, задержать ответ API | Индикатор виден, ложное пустое состояние не показывается |
| Список | Вернуть несколько элементов | Верные данные и порядок, нажатие открывает нужный id |
| Пусто | Вернуть успешный пустой список | Сообщение об отсутствии данных и возможность обновления |
| Ошибка | Вернуть 500 или сетевой сбой | Понятная ошибка и кнопка повтора |
| Повтор | После ошибки вернуть успешный ответ | Ошибка исчезла, данные показаны, лишних запросов нет |
| Обновление | Свайпнуть список, вернуть новые данные | Индикатор завершается, список обновлен без дублей |
| Ошибка обновления | Сбой после ранее успешной загрузки | Старые данные сохранены, видна ошибка обновления |
| Поворот | Повернуть устройство при загрузке и при списке | Нет переполнения и дублирующей загрузки; сохранено состояние по требованиям |
| Возврат | Открыть подробности и вернуться | Сохранены позиция/фильтр; измененный элемент актуализирован |
| Уход при запросе | Закрыть экран до ответа | Запрос отменен, нет setState after dispose |
| Быстрая смена фильтра | Второй ответ приходит раньше первого | Показан результат последнего фильтра |

Автоматически: unit-тесты контроллера и repository, widget-тесты состояний и нажатий с fake API, интеграционные проверки навигации и жизненного цикла. Поворот и восстановление проверить на эмуляторе или устройстве.
Вручную: читаемость, плавность, удобство свайпа, экранный диктор, крупный шрифт и разные реальные устройства. Автотесты и ручные проверки дополняют друг друга.
